# 横店影视 AIGC 门户

v0.5 内部可用版。面向横店中小剧组与创作者，将 AI 工具按影视工作流重新组织。
两个模块：

- **AI 工具库**（纯前端）：场景浏览、搜索筛选、官网直达、本机收藏。回答「有哪些工具、去哪用」。
- **AI 工作流**（需后端）：填参数、提交、在站内拿到产出。回答「不出门户就把活干了」。
- **画布**（需后端）：节点画布。素材、动作与产出连成一张图，上游改了下游自动标脏。
  回答「一次没出对，接着改，且改完知道哪些东西已经不对了」。

> 当前版本是内部体验与需求验证用的站点，不是生产系统。
> 本机档案只保存一个显示名称，不设置密码，也不构成身份认证。
> 工作流账号是另一套：它存在门户后端，用于归属任务与控制额度。
> 两处都请勿录入项目秘密或个人敏感信息。

## 本地运行

```bash
npm install
npm run validate:data     # 工具底表 + 工作流定义双重门禁
npm run typecheck
npm test
npm run dev               # http://localhost:3000
```

工作流需要后端一起起：

```bash
cd server && npm install && cp .env.example .env && npm run dev
```

前端默认在开发模式下连 `http://localhost:8787`。正式构建需设 `VITE_PORTAL_API` 指向已部署的后端；
未设置时工作流页面显示「后端尚未部署」的说明，工具库与收藏不受影响。

## 演示模式

GitHub Pages 是静态托管，跑不了后端，而工作流恰恰需要后端。构建时置 `VITE_DEMO_MODE=true`
后，工作流的请求由浏览器内的演示后端应答：

```bash
VITE_DEMO_MODE=true npx vite build --config vite.config.build.ts
```

- 拦截点在 `src/lib/portalApi.ts` 的 `api()` 一层，页面、表单、轮询、错误处理走的
  是与真实后端完全相同的代码路径；参数校验复用同一份 `workflows.json` 声明。
- 只有「生成」这一步是本地模拟：产出为内联 SVG 与占位文本，不联网、不产生费用。
- 免登录，直接以「演示账号」进入；数据存 sessionStorage，关闭标签页即清空。
- 工作流三页顶部常驻醒目横幅说明这是演示产出，并提供「重置演示数据」。
- 演示后端是独立 chunk（约 5 KB），关闭演示模式的正式构建不会把它打进主包。

三种构建的取舍：

| 场景 | 构建参数 | 工作流表现 |
| --- | --- | --- |
| 本地开发 | 无 | 连 `localhost:8787` 真后端 |
| 演示站 / GitHub Pages | `VITE_DEMO_MODE=true` | 完整可点，产出为本地占位内容 |
| 正式部署 | `VITE_PORTAL_API=https://…` | 连真后端与真算力 |

`.github/workflows/deploy.yml` 当前用的是演示模式。后端有了公网落点后，把那里的
`VITE_DEMO_MODE` 换成 `VITE_PORTAL_API` 即可。

生产构建：

```bash
npm run build
npm run preview
```

## v0.5 范围

工具库部分（v0.2 起）：

- 首页：产品定位、六大场景入口、显式精选工具。
- 工具库：名称/简介搜索，按一级分类、场景和复核状态筛选。
- 我的收藏：建立本机档案后，在当前浏览器保存工具收藏；未建档时点击收藏，建档完成后会自动接续该操作。
- 关于页：数据来源、编辑复核边界和当前版本限制。
- 数据层：保留 473 条来源底表，叠加 50 条核心复核、2 条空入口待复核和 2 条重复排除记录。

画布部分（v0.5 起为节点画布）：

- `/canvas`：画布列表，新建、重命名、删除。
- `/canvas/:id`：基于 React Flow 的节点画布。三类节点（图片 / 视频 / 文本），
  左进右出连线，平移缩放、小地图、按拓扑自动整理。
- 节点可绑定一个动作（工作流）。没绑动作的就是素材节点，只作为下游输入。
- **连线即输入槽位**：上游按类型编号成「图 1」「文 1」，图片类上游自动作为原图送进去，
  提示词里写 `{{文 1}}` 就能引用上游文本。一份提示词模板可以在不同上游之间复用。
- **脏标记**：上游产出变了，全部下游标成「上游已更新」并高亮边框，重跑即可对齐。
  没有这一步，画布上摆的就是一堆来源不明的旧图。
- 局部重绘的选区在检视面板里框（显示的是上游那张图），选区因此明确属于这个节点。
- 变更防抖聚合后批量落库；多个节点同时生成时用一个批量接口轮询，不是每个节点一个定时器。

工作流部分（v0.3 新增）：

- `/workflows`：6 条流水线，按场景筛选，显示预计耗时与额度消耗。
- `/workflows/:slug`：由定义文件驱动的参数表单，提交后就地轮询结果，可取消。
- `/runs`：我的任务与产出，有任务进行中时自动刷新。
- 工作流账号：登录、注册、退出，与本机档案并存（见下文）。

不在本版本范围：横店统一认证、跨设备收藏同步、工具付费代购、自动可用性监测、
本地文件上传、产出资产库、自建 GPU 与算力调度、AI 助手侧栏（Agent 直接在画布上建节点）、
故事板视图、把子图打包成可复用工作流。

## 本机档案与收藏

- 本机档案只填写 2–20 个字符的显示名称，无密码体系，不代表真实人员身份。
- 当前数据键为 `hd_profile_v1` 和 `hd_favorites_v1`。
- 新键首次不存在时，系统只复制旧 `hd_session` 及对应 `hd_favs_<username>` 的可兼容数据；旧键不会被删除或覆盖。
- 主动关闭本机档案后会保留明确的空档案状态，避免旧数据在后续访问中被再次误迁移。
- `localStorage` 不可用或读写失败时，系统降级为当前页面内存存储并显示提示；刷新或关闭页面后，这部分临时数据可能丢失。
- 未建档时触发的收藏会记录为待完成操作；保存档案后，目标工具自动加入“我的收藏”并给出反馈。

## 六大场景与稳定 slug

中文名称是展示文案，URL 查询参数和持久化逻辑应优先使用稳定 slug。

| 中文场景 | slug |
|---|---|
| 剧本创作 | `scriptwriting` |
| 概念美术 | `concept-art` |
| 视频生成 | `video-generation` |
| 后期制作 | `post-production` |
| 宣发物料 | `promotion` |
| 综合效率 | `productivity` |

`parseSceneParam()` 同时兼容稳定 slug、中文场景名、URL 编码中文和 v0.1 常见短写。

## 两套身份，为什么不合并

| | 本机档案 | 工作流账号 |
| --- | --- | --- |
| 存在哪 | 当前浏览器 `localStorage` | 门户后端 SQLite |
| 有无口令 | 无 | 有 |
| 用途 | 工具收藏 | 归属工作流任务、控制额度、限定产出可见范围 |
| 换设备 | 丢失 | 保留 |

本机档案对外承诺「无密码、不上传」，工作流则必须能把每一次算力调用归到具体账号上，
两者的安全承诺不同，用同一个抽象会让其中一边的承诺失真。
合并是产品决策（需要改掉本机档案的对外口径），不在工作流这一期内顺手做掉。

## 工作流数据结构

- `src/data/workflows.json`：**工作流定义的唯一来源**。前端渲染表单、后端校验参数与派单都读这一份。
- `src/data/workflows.ts`：类型、场景/工具关联、前端即时校验。
- `scripts/validate-workflows.mjs`：定义门禁，随 `npm run validate:data` 执行。

新增一条工作流只改 JSON，不改任何组件代码。定义里声明的约束（必填、长度、取值范围、
数字上下限）由前后端各自解释同一份声明，而不是各写一套硬编码规则。

### 画布操作为什么也是工作流

局部重绘、扩图、生成变体在定义文件里就是三条 `surface: "canvas"` 的工作流。
这样队列、每日额度、provider 适配、埋点与周报统计全部复用既有那一套，
画布不需要第二条执行链路。差别只有两点：

- 它们不进 `/workflows` 列表页（`GET /api/workflows` 默认只返回 `surface=library`）。
- 标了 `supplied: "canvas"` 的字段（`sourceUrl` 与选区坐标）由画布按当前选中图与
  选区自动填入，界面不渲染——让用户手填「选区左边距 37.2%」没有意义。
  服务端仍照常校验这些字段，缺了会逐字段报错。

因此新增一个画布操作同样只改 JSON：加一条 `surface: "canvas"` 的定义即可。

门禁强制的几条：

1. 文本字段必须声明 `maxLength`，数字字段必须同时声明 `min` 与 `max`——
   没有上限的参数会原样变成算力账单。
2. 下拉框至少两个选项，默认值必须落在选项内。
3. `relatedToolIds` 必须指向 `tools.json` 里真实存在的工具。
4. 每条工作流至少一个必填字段，否则无法判断提交是否有效。
5. `costCredits` 必须为正整数，配额按它扣减。
6. `surface` 只能是 `library` 或 `canvas`；画布操作必须有由画布填入的 `sourceUrl`，
   必须以图片为产出，且至少留一个用户可调的参数——否则它就只是个没得调的按钮。
7. `supplied: "canvas"` 的字段必须是必填：可选的话忘了填也不报错，问题会推迟到算力方才暴露。

## 数据结构

- `src/data/tools.json`：473 条来源底表。保持来源字段，不在此文件中混入推荐判断。
- `src/data/tool-editorial.json`：v0.2 编辑复核层，包含 50 条核心白名单、13 条精选白名单、2 条空入口待复核、2 条重复排除，以及推荐场景、理由、权重、日期和 canonical URL。
- `src/data/scene-rules.json`：未进入核心集的工具使用的保守关键词初筛规则和 16 个明显错标回归样例。
- `src/data/tools.ts`：将底表与编辑层合并为页面使用的 `effectiveTools`，并在不改动来源底表的前提下清理所有展示外链中的常见跟踪参数。
- `scripts/validate-tools.mjs`：校验 ID、分类、场景、核心集、精选白名单，并汇总空/非法/重复 URL 与已清理跟踪参数数量。

本轮编辑复核覆盖名称、官网域名、产品定位与影视工作流适配；它不等同于实时可用性监测、采购背书或合规审查。未进入核心集的工具仍可浏览，状态为 `unreviewed`，场景由名称与简介关键词做规则初筛。来源底表的旧 `scenes` 只用于追溯，不直接驱动页面筛选。

复核状态：

| 值 | 含义 |
|---|---|
| `verified` | 已完成本轮复核 |
| `needs-review` | 待复核 |
| `excluded` | 明确重复、错标或无可用入口，不进入有效集合 |
| `unreviewed` | 未进入本轮复核 |

精选不是由权重或热门度自动推断，必须显式进入 `featuredToolIds` 白名单，且状态必须为 `verified`。

## 数据 API

```ts
import {
  effectiveTools,
  featuredTools,
  SCENE_DEFINITIONS,
  parseSceneParam,
  VERIFICATION_STATUS_LABELS,
} from '@/data/tools'
```

主要导出：

- `effectiveTools: EffectiveTool[]`：页面唯一应使用的有效工具集合。
- `tools`：兼容 v0.1 的别名，指向 `effectiveTools`。
- `SCENE_DEFINITIONS` / `SCENES`：场景定义和中文场景列表。
- `parseSceneParam(value)`：把中文或 slug 参数归一为 `SceneSlug`。
- `inferSceneSlugs(tool)`：对未进入核心编辑层的工具执行保守场景初筛。
- `CORE_TOOL_IDS` / `FEATURED_TOOL_IDS`：显式核心和精选白名单。
- `coreTools` / `featuredTools` / `toolById`：常用派生集合。

`EffectiveTool` 在来源字段之外增加：`sceneSlugs`、`verificationStatus`、`verifiedAt`、`recommendationReason`、`sortWeight`、`featured` 和 `editorial`。

## 数据改动门槛

1. 来源抓取更新只改 `tools.json`，编辑判断只改 `tool-editorial.json`。
2. 新增场景必须同步 `SCENE_DEFINITIONS` 和验证脚本中的合法 slug。
3. 修改未复核工具的场景规则时，必须在 `scene-rules.json` 补充或通过对应回归样例。
4. 精选工具必须先进入 50 条核心白名单并完成本轮复核。
5. 核心 canonical URL 不得保留 `utm_*`、`ref`、`via` 等跟踪参数。
6. 所有页面外链统一经过 `sanitizeToolUrl()`；空入口必须显式标为 `needs-review` 并说明原因。
7. 提交前至少运行：

```bash
npm run validate:data
npm run typecheck
npm run lint
npm test
```

改动后端时另需在 `server/` 跑 `npm run typecheck && npm test && bash scripts/smoke.sh`。

## 已知限制

- 节点画布不做版本快照与协同编辑：同一画布多端同时打开会互相覆盖，以最后落库的为准。
- 画布上的图记录的是图片链接，不转存文件。算力方的产出链接可能有有效期，
  过期后画布上会显示为裂图；需要长期保存请及时下载。
- 画布图片只接受公网 http(s) 链接或内联图片数据，尚不支持本地文件上传。
- **线上演示站（GitHub Pages）跑的是演示模式**，工作流产出是浏览器本地生成的占位内容，
  既不代表模型真实效果，也不代表实际生成耗时。
- **工作流产出由第三方模型生成**，版权、授权范围与商用条件以对应厂商条款为准，门户不做背书。
- 后端未配算力凭据时，工作流回落到「演示算力」，产出是明确标注的占位内容，不是真实生成结果。
  线上部署必须设 `WORKFLOW_ALLOW_MOCK=false`。
- 工作流参考图只接受公网 http(s) 链接，尚不支持本地上传；产出链接由算力方托管，可能有有效期。
- 来源底表是一次性快照，未自动检测官网失效、跳转变化或产品下线。
- 工具说明和推荐理由用于内部导航，不代表横店、数据来源站或项目组为厂商背书。
- 工具官网的价格、账号、生成内容、版权、数据出境与隐私政策由相应厂商负责，正式使用前仍需单独评估。
- 本机档案不是身份体系；清理浏览器数据会丢失档案和收藏，内存降级状态下刷新页面也可能丢失临时数据。
